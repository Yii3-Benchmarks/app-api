Run notes

Run note (2026-10-08). React HTTP 1.11.1 uses a return-type-only PSR-7 v2 compatibility patch isolated to its Docker image; Amp HTTP Server is 3.4.6 with Revolt 1.0.9. Both use 20 Supervisor-managed PHP processes, SO_REUSEPORT, TCP_NODELAY, Event 3.1.6, and recycling after 10,000 requests. Yii and PDO handling remains synchronous, with per-request state reset and native request concurrency limited to one per process. This separate October 8 session uses the same PHP 8.5.11 and load settings as the earlier measurements; existing runtimes were not rerun.

Run note (2026-10-08). Both runtimes recorded socket read errors while recycling workers. Amp also recorded non-success HTTP responses; its native graceful shutdown can send 503 responses to queued requests. All recorded errors are retained and reduce successful RPS using the existing report calculation. No PHP application errors were logged during measurement.

Charts show raw samples. For stage results, RPS cap marks the first stage with successful throughput more than 5% below target; per-second results use a sustained latency surge. The load generator can also limit throughput.

Calculation details

For stage data, each sample represents one load stage. The first stage provides the latency baseline. A surge is detected when average latency reaches the largest of 20 ms, 4× baseline average latency, or baseline average latency + 12 ms. When baseline p95 is available, the stage must also have a p95 reaching the largest of 30 ms, 2.5× baseline p95, or baseline p95 + 15 ms. These thresholds are a heuristic, not a latency guarantee.

Normal averages exclude the first qualifying surge stage and all later stages, or stop earlier at the throughput cap. If the cap occurs in the first stage, no normal measurement is available. If no cap is reached, no overloaded measurement is available. For per-second data, the existing sustained latency-surge detector determines the cutoff, and averages use per-second samples.
